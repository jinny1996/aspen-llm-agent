# 연구 설계안 v0 — Evidence-grounded DoF Closure (가칭 EDC)

작성: 2026-10-06 / 상태: 초안 (선행연구 조사 1차 + 코드 확인 반영, 지도교수 논의 전)

## 1. 한 줄 주장

문헌에서 공정 모델을 만들 때 **빠진 자유도(DoF)를 "근거가 있는 값 / 유도한 값 / 가정한 값 / 사용자에게 물은 값 / 시뮬레이터 기본값"으로 구분해 채우고, 시뮬레이터가 암묵적으로 채운 기본값까지 감사**하면, 일반 목적함수로 채우거나(ETH) 개수만 맞추는(CRAFTS) 방식보다 논문 보고 수치에 더 충실한 모델이 나온다.

논문 수치 비교는 기여가 아니라 **이 주장을 재는 평가 도구**로 쓴다.

## 2. 선행연구 대비 위치 (읽은 원문 기준)

| | 빠진 DoF 처리 | 한계 (원문이 직접 언급/드러난 것) |
|---|---|---|
| Text-to-flowsheet (ETH, Digital Discovery 2026) | 블랙박스 최적화(차분진화), 목적함수=수렴+에너지/용매 최소화. 실패 시 유닛 단순화(rigorous→shortcut→Sep). 사람 확인 없음 | 목적함수가 일반적이라 논문 값과의 일치를 보지 않음. 아닐린 공정에서 공비 불일치를 발견하고도 "향후 과제"로 남김. 순차 설계라 시뮬레이션 후에야 드러나는 문제 처리 곤란(본인들 서술) |
| CRAFTS (NUS, arXiv 2608.01369) | Specification Agent가 값을 제안, DoF 검사기가 **개수만** 확인(expected DoF=0). 제안값에 "ChE-agent/DoF-validated" 표식 | 값의 근거 유무는 검사하지 않음. IDAES 기반. ChE 지식 제거 시 성공률 91.5%→0%, 디버그 제거 시 18.3% (지식·복구가 결정적). 지식은 사람이 큐레이션한 정적 지식 |
| Agentic Scientific Simulation (SINTEF, arXiv 2603.00214) | 모호함 탐지 → 가정 로그 또는 사용자 질의 | **시뮬레이터 기본값으로 암묵 처리된 선택은 로그에 안 남음**(핵심 열린 문제로 명시). 기본값 체크리스트를 제안만 하고 구현 안 함. 저류층 도메인 |

**ACS Copilot (Kang et al., I&ECR 2026, 65, 16718; 본문 20/21쪽 읽음, SI 미열람)**
- Claude Sonnet 4.5 + MCP 도구 42개 + 계층형 Skills 지식. 사람이 단계마다 개입하는 협업형.
- 문헌 재구성은 **사례 1개**(IPA 추출증류, Liang et al.). 프롬프트가 "그림 9b의 절댓값을 쓰고 계산·추정하지 말라"고 지시. 결과: 열부하 오차 0.03/1.56/1.29%, 구조 충실도 100%.
- 에이전트가 논문에 없는 사양 5개(단 번호 방향, 응축기 종류, DMSO 보충 유량, 컬럼 압력강하, 열교환기 최소 접근온도)를 자유 서술로 나열. **SI(35쪽 전체 확인) 결과: 나열 이후 항목별 해결 기록이 없음.** SI Stage 5~6에서 확인되는 것은 보충 유량(0.0001 kmol/h 입력)과 C1 응축기(TOTAL)뿐이고, 단 번호 방향·C2/C3 응축기·압력강하·접근온도의 처리는 기록되지 않음(Aspen 기본값에 맡겼는지, 에이전트가 정했는지 알 수 없음 = SINTEF이 지적한 "암묵 기본값" 문제가 그대로 나타남).
- 보충 유량 불일치 관찰: SI 실행은 0.0001 kmol/h, 본문 Table 17의 문헌 사양은 2.005×10⁻⁴ kmol/h. 어느 쪽이 원 논문(Liang et al.) 값인지는 확인 못 했으나, 나열 단계에서 "누락"으로 분류한 값이 본문 표에는 있음.
- 사례 3은 논문이 거의 완전한 사양(RR과 D 모두)을 제공하고 사용자가 "계산·추정 금지"를 지시한 **쉬운 설정**. DoF가 실제로 비는 경우(사례 1·2: 사용자 요청만 있음)는 에이전트가 단수 40, 환류비 4.0, D/F 0.121 등을 임의 선택(저자 본문도 "LLM이 임의로 선택"이라 서술)하고 목표 순도를 향해 반복 조정. 근거 추적 없음.
- 누락 장비(냉각기)와 몰/질량 분율 혼동은 **사용자가 발견**.
- 한계(원문 명시): 반응 공정 미지원, 모델 1종, 사용자 연구 없음. 순도를 맞추려 환류비를 0.518→0.65로 바꾸자 C2 열부하가 논문 대비 약 +5%(1098.2→1156.4 kW)로 벌어짐 (순도 목표 vs 논문 충실도 충돌).
- Skills의 "Common Errors"는 관찰된 실패에서 **저자들이 반복 수정하며 수작업으로** 만든 것.
- 시사점: 문헌 재현 단독은 기여가 못 됨(평가 지표로는 유효). DoF 공백 탐지가 LLM 판단+사람 의존이라는 점이 EDC의 근거. 실패→지식 변환이 수작업이라는 점이 D의 근거.

미확인: SNU Aspen MCP는 DoF를 다루지 않음. CRAFTS 부록·ETH SI는 미열람.

**2차 선행연구 검색 (2026-10-06, 키워드 변경 4건, 웹검색 요약 기반 — 원문 정독 아님)**
- EDC 쪽: DoF 공백을 "문헌 근거로 분류·추적하며 폐쇄"하거나 "시뮬레이터 기본값을 감사"하는 화학공정 LLM 연구는 추가로 발견되지 않음. 검색에 걸린 것은 이미 읽은 ETH/CRAFTS/SINTEF뿐. (검색 도구가 arXiv·일부 저널 위주라 Scopus/Web of Science 수준의 망라는 아님 → 투고 전 사서/지도교수 수준의 체계적 검색 필요)
- D 쪽 **겹침 발견**: 검증 통과 후에만 메모리에 저장하는 방식 자체는 이미 존재.
  - ChipMEM (arXiv 2609.27067, EDA 에이전트): 합성/시뮬레이션/형식검증을 통과한 스킬만 절차 메모리에 저장 + 오류 맥락별 복구 전략 순위(베타 분포). 효과는 크지 않음(39/54 vs 35/54 통과, held-out 20/20 vs 18/20). "같은 과제 반복 접근은 과제 특화 수정을 보상할 뿐 이전 가능한 지식을 못 만든다"는 문제의식 → **평가 설계 시 동결 라이브러리 + held-out 과제 필수**.
  - MemGuard (arXiv 2608.21867): 검증 신호를 메타데이터로 저장해 검색·충돌해소·요약·보관 전 생애주기에 사용. 범용 벤치마크(SWE-Bench 등).
  - 일반 에이전트 메모리 문헌에서 "순진한 누적은 오류 전파"가 이미 정설.
  → **D의 메커니즘(검증 게이트 메모리)은 노벨티가 아님.** 남는 차별점은 (1) 화학공정 시뮬레이션 도메인 최초 적용 여부(이번 검색에서 못 찾음), (2) 도메인 고유 검증자(Aspen 수렴 + 논문 수치 일치 + 근거 장부)를 게이트로 쓰는 설계, (3) EDC 장부와 결합된 "근거 있는 가정"의 재사용. 즉 D 단독은 약하고 EDC와 결합해야 의미.

## 3. 현재 시스템 갭 (코드 확인 결과)

확인한 사실:
- `Schema_v5.yaml`에 **출처 필드가 이미 있음**: `source ∈ {paper, inferred, default, llm, user}`, `confidence`, `evidence{doc_id, locator, quote}`, `rationale` (feeds, block specs 전반). → 새 스키마 설계 불필요, **활용도를 높이는 것**이 과제.
- 그러나 Part1 초안 프롬프트는 `source`를 `"paper"|"llm"` 두 값으로만 제시 (`part1_stage_functions.py:1827`). 5분류가 실제로는 쓰이지 않을 가능성이 큼 (실제 산출물 분포는 미확인).
- 사람 확인 대상 선정은 `collect_schema_human_review_items` (`part1_stage_functions.py:2350`)가 담당: source가 llm/default/inferred이고 confidence ≤ 0.45(또는 null)이며 핵심 필드인 항목을 최대 8개 추림. → **confidence 임계값 휴리스틱**이지 DoF 기반이 아님. LLM 자기 보고 confidence에 의존.
- Part2 검증기(`valid_*_rules.yaml`)는 **Aspen COM 데이터 트리를 만든 뒤** 검사 (registry의 입력이 Aspen `doc` 핸들). 블록 단위(`SPEC_OPT` 허용 조합과 조합별 필수 입력, 피드 T/P/조성 완비)만 봄. 플로우시트 전체의 필요 사양 수 vs 제공 사양 수 계산은 없음.
- 스키마 v5의 블록 종류는 9개이고 **RADFRAC 없음**. `Schema_v5.1(rad).yaml`에는 RADFRAC가 있으나 현재 파이프라인(phase12) 사용 여부는 미확인. 증류탑은 자유도 문제가 가장 큰 블록이라 범위 결정이 필요.
- Aspen 기본값이 암묵적으로 쓰이는 부분을 감사하는 기능: 없음.

## 4. 제안 방법

### 4.1 DoF 장부(ledger)
- 블록 유형별 "필요 사양 집합"을 규칙에서 도출: 기존 `valid_block_rules.yaml`의 `SPEC_OPT` 조합(예: FLASH2는 TP/TV/PV/TD/PD/PQ/TQ 중 하나 + 해당 필수 입력)을 확장해 **블록마다 선택 가능한 완결 사양 패턴**을 열거.
- 플로우시트 수준: 피드 사양(T, P, 유량/조성), 스플리터 분율, 반응기 전환율/온도/압력, 압력 변화 등을 합쳐 `필요 변수 − 제공 변수 = 공백(gap)` 목록 생성. 순수 스키마 분석이라 **API·Aspen 비용 없이 구현/테스트 가능**.
- 위치: Part1 스키마 확정 직후, Part2 COM 빌드 이전의 사전 게이트.

### 4.2 값의 분류 (장부의 각 변수)
| 분류 | 정의 | 요구 증거 |
|---|---|---|
| STATED | 논문에 명시 | 원문 인용(quote)이 논문 텍스트에 실제로 존재 (문자열 일치로 검증) |
| DERIVED | 명시된 값에서 계산 (물질수지, 전환율 환산 등) | 입력 변수 참조 + 계산식 |
| ASSUMED | 공학 관례값 (펌프 효율 등) | 근거 문구/출처 + 영향도 등급 |
| ASKED | 사용자 답변 | 대화 로그 |
| ENGINE-DEFAULT | 우리가 지정하지 않아 Aspen이 기본값을 쓴 항목 | 4.3의 감사로 발견 |

### 4.3 시뮬레이터 기본값 감사 (SINTEF이 못 푼 부분)
- Aspen 데이터 트리의 블록/스트림 Input 노드를 순회해 "우리 스키마가 지정한 것" vs "지정되지 않았지만 계산에 쓰이는 것"을 대조 (`valid_feed_rules.yaml`이 이미 `Specified` 키로 지정 여부를 읽는 방식을 쓰고 있어 같은 접근이 가능해 보임).
- 발견된 기본값은 ENGINE-DEFAULT로 장부에 올리고, 영향이 큰 것(민감도 또는 규칙 기반 등급)만 보고/질문 대상으로 승격.
- **타당성 미검증**: 데이터 트리에서 기본값 사용 여부를 안정적으로 구분할 수 있는지 먼저 소규모 실험 필요 (EDC-3 선행 실험).

### 4.4 질문 정책 (질문 최소화)
- 현행 confidence 임계값 방식을 **"근거 없음(STATED/DERIVED 아님) AND 영향도 높음"** 기준으로 교체.
- 영향도 1차: 규칙 기반 등급 (반응기 전환율, 분리 사양 = 높음 / 펌프 효율 = 낮음). 2차(선택): 소수 시뮬레이션으로 민감도 측정.
- 평가 지표로 "질문 수 vs 최종 편차" 곡선을 그림.

### 4.5 산출물
- 모델(.bkp)과 함께 **가정 장부**(JSON + 사람이 읽는 요약): 변수별 분류, 값, 근거, 영향도. 챗봇 최종 응답에 요약 포함.

## 5. 평가 설계

### 5.1 비교 조건
| | 방식 | 비고 |
|---|---|---|
| C0 | 현행 (confidence 임계값 + 8개 상한) | 내부 baseline |
| C1 | ETH식: 공백을 일반 목적함수 최적화로 채움 | **재구현 필요**. 원 논문 방식의 단순화 버전임을 명시 (CRAFTS도 타 방식을 재구현해 비교함) |
| C2 | CRAFTS식: LLM이 값 제안, 개수만 검사 | 재구현, 위와 동일 |
| C3 | EDC (제안) | |
| (선택) | 범용 에이전트(frontier 모델 + COM 직접) | 초기 우려("Claude로 그냥 되지 않나")에 대한 참고 비교. 주 실험 아님 |

### 5.2 지표
1. **논문 보고 수치와의 편차** (스트림 조성, 열부하, 전환율 등 논문 표/그림의 KPI) — 주 지표
2. **장부 정확도**: 사람이 라벨링한 부분집합에서 분류가 맞는 비율, STATED 인용의 실재율
3. **질문 효율**: 질문 수 대비 편차 감소
4. **기본값 감사 커버리지**: 발견된 ENGINE-DEFAULT 수, 그중 KPI에 유의한 영향(예: >x%)을 주는 비율
5. 수렴 성공률, 비용(토큰/시간)

### 5.3 벤치마크
- 논문 8~10편 이상 (현재 ATR 1편만 실전 검증됨). 선정 기준: Aspen으로 시뮬레이션했고, 수치 KPI를 표/본문에 보고하며, 사용 가능한 property method가 우리 범위에 들어오고, 공백 규모가 다양할 것.
- 정답(gold): 논문 보고 값. 변수 단위로 "논문에 명시/비명시" 사람 라벨링.
- 학습/튜닝용과 최종 평가용 분리 (D를 도입하면 필수).

### 5.4 Ablation
출처 분류 제거 / 질문 정책 제거 / 기본값 감사 제거 / 장부 없이 confidence 방식 (C0).

## 7. D(경험 누적)와의 연결 — 확장 카드

- EDC가 만드는 장부에서 "시뮬레이터 수렴 + 논문 수치 일치"로 검증된 해결 사례(변수 X, 블록 Y, 값 Z, 근거)를 지식베이스에 누적 → 다음 논문의 ASSUMED 값 제안과 실패 복구에 재사용.
- 오염 방지: **검증을 통과한 사례만 저장**(일반 에이전트 메모리 문헌의 오류 전파 문제에 대한 도메인 고유 해법).
- 비교축: CRAFTS의 사람 큐레이션 정적 지식 vs 자동 누적 지식. 학습 곡선(논문 순서대로 처리하며 성능 변화), 메모리 on/off, 평가 논문 분리 필요.
- 선행연구 근거: CRAFTS(ChE 지식 제거 시 성공률 91.5%→0%, 지식은 사람이 큐레이션), ACS Copilot(Skills의 오류 목록을 저자가 실패 관찰 후 수작업으로 개선). 두 연구 모두 "실패→지식" 변환이 수작업 → 이를 검증 기반으로 자동화하는 것이 차별점.
- 2차 검색 결과: 검증 게이트 메모리 메커니즘은 ChipMEM/MemGuard가 선점(위 §2). 따라서 D는 "방법론 신규"가 아니라 "화학공정 도메인 적용 + 도메인 고유 검증자 + 근거 장부 연계"로만 포지셔닝 가능. 평가는 ChipMEM 교훈(동결 라이브러리, held-out 논문)을 따를 것.
- EDC만으로 기여가 부족할 때 투입. 평가 설계가 무거워 EDC 완료 후 판단.

## 8. 리스크와 미결정 사항

1. **노벨티 잠정 양호, 미확정**: 읽은 5편(ETH, CRAFTS, SINTEF, ACS 본문+SI) 모두 DoF 공백을 근거 기반으로 폐쇄/감사하지 않으며, 2차 검색(4건)에서도 추가 발견 없음. 단 검색 도구 한계(웹검색 요약, 주로 arXiv)로 "없다"의 증명이 아님. 문헌 재현 자체는 ACS가 1건 수행했으므로 단독 기여로 주장 불가. D의 검증 게이트 메모리 메커니즘은 ChipMEM/MemGuard가 선점.
2. **기본값 감사의 실현 가능성** 미검증 (EDC-3 선행 실험으로 확인).
3. **블록 범위**: 스키마 v5에 증류탑이 없으면 DoF가 가장 어려운 사례가 빠져 주장이 약해질 수 있음. 반대로 포함하면 구현 범위 증가.
4. **정답의 한계**: 논문 보고 값이 정답이라는 가정. 논문 자체의 오류/불완전성, property method 차이로 일치가 불가능한 경우의 처리 기준 필요.
5. **재구현 baseline의 공정성**: C1/C2는 원 시스템이 아님. 한계 명시, 가능하면 공개 코드 확인.
6. **평가 규모**: 논문 수가 적으면 통계적 주장이 약함. 비용과 논문 확보량의 균형.
7. 지도교수와 논의 필요: 주 기여 구성(EDC 단독 vs EDC+D), 목표 저널/학회.

- 발견: Part2 검증기(`valid_block_rules.yaml`)에는 SPLITTER, VALVE 규칙이 없음. 장부는 스키마 수준에서 둘 다 다룸.
