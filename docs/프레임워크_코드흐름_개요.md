# 프레임워크 코드 흐름 개요

작성: 2026-10-08 / 기준: `2609 수정/phase13` (코드를 직접 읽고 작성. 줄 번호는 이 시점 기준)

## 1. 전체 구조 한눈에

```
[Gradio app.py] ──(워커 스레드 1개, COM 스레드 고정)──▶ [PipelineSession.handle_user_message(text)]
                                                              │  (chat_orchestrator.py)
        ┌─────────────────────────────────────────────────────┼──────────────────────────────┐
        ▼ stage="part1"                                       ▼ stage="part2"                ▼ stage="part3"
  tool-calling 에이전트 루프                            tool-calling 에이전트 루프        tool-calling 에이전트 루프
  (LLM이 도구를 골라 호출)                              (LLM이 도구를 골라 호출)          (LLM이 도구를 골라 호출)
        │                                                     │                              │
  part1_stage_functions.py                              part2_stage_functions.py        part3_stage_functions.py
  (논문→스키마 YAML)                                     (스키마→Aspen COM 모델)          (Aspen 실행 로그→진단·패치)
        │                                                     │                              │
        └──── Schema_validated.yaml ──────────────────────────┘                              │
                                      └──── .bkp (Aspen 모델) ───────────────────────────────┘
                                                                                             ▼
                                                                                  최종 .bkp + [가정 요약]
```

핵심 설계 원칙은 세 가지다.
1. **한 개의 살아 있는 프로세스**가 턴마다 호출된다. 사람이 필요한 지점은 "함수가 리턴하고 다음 사용자 메시지를 기다리는 것"으로 처리한다.
2. **LLM은 도구를 고르고 순서를 정할 뿐**, 실제 작업은 일반 파이썬 함수(stage functions)가 한다.
3. **세션 상태는 파트별 `session` dict에 모이고**, 중간 산출물은 파일(YAML/JSON/.bkp)로 남는다.

## 2. 진입점과 실행 방식

| 파일 | 역할 |
|---|---|
| `app.py` | Gradio UI. 전역 `PipelineSession` 1개. `_PipelineWorker`가 전용 스레드 1개를 만들어 모든 턴을 그 스레드에서 실행(Aspen COM은 `doc`을 만든 스레드에서만 호출 가능, 스레드 시작 시 `CoInitialize`). 진행 상황은 `progress_q` 큐로 실시간 스트리밍 |
| `chat_orchestrator.py` | `PipelineSession`: 세 파트를 한 프로세스 안에서 차례로 실행. CLI(`python chat_orchestrator.py`)로도 실행 가능 |
| `run_case.py` | 실험용 터미널 실행기. 케이스 A/B/C의 논문·그림·첫 프롬프트를 고정하고 `--part1-only --auto-ok --reply` 지원 |
| `agent_loop_utils.py` | 직접 만든 ReAct 루프 `run_tool_calling_agent` / `resume_tool_calling_agent`, 일시정지 예외 `HumanInputRequired` |
| `mcp_server.py`, `mcp_call_tool.py` | 검증·컨텍스트 도구를 MCP 서버(stdio)로 노출. 각 파트의 `mcp_client_tool_call`이 자식 프로세스(`mcp_call_tool.py`)를 띄워 호출. `MCP_ADAPTER_MODE`로 로컬 어댑터와 전환(PipelineSession 기본값은 `local_adapter`) |
| `experiment_logging.py` | `record_event`로 이벤트 기록(실험 로그) |

### 에이전트 루프와 사람 개입(HITL)
- `run_tool_calling_agent`: `llm.bind_tools(tools)` → 모델이 도구 호출 → 같은 스레드에서 `tool.invoke` → 결과를 `ToolMessage`로 되돌림 → 도구 호출이 없으면 종료. 최대 스텝 제한(Part1 25, Part2·3 40).
- 도구가 `HumanInputRequired(payload)`를 던지면 루프가 `status="paused"`로 리턴. `PipelineSession`이 `self.pending`에 (llm, tools, messages, pending_tool_call)을 저장하고 질문을 채팅에 표시.
- 다음 사용자 메시지가 오면 `resume_tool_calling_agent`가 **같은 도구를 `human_answer=사용자 메시지`와 함께 다시 호출**해 정상 부기를 하고 루프를 이어간다.
- 각 파트의 `*_HITL_MODE=chat` 환경변수로 이 모드를 켠다(배치용 `bypass`는 자동 승인).

### 파트 전환
`_handle_agent_result` → 루프가 `done`이면 `_finish_partN`이 결과 파일을 확인하고 곧바로 다음 파트의 `_start_part(N+1)`을 호출한다. 실패하면 `stage="done"`으로 멈추고 오류 메시지를 낸다. 전환 사이의 진행 문구는 `on_narration` 콜백으로 UI에 흘려보낸다.

## 3. Part1 — 논문 → 공정 스키마 (`part1_stage_functions.py`)

**LLM 도구 순서** (시스템 프롬프트가 권장):

```
fetch_paper_context → assess_input_readiness ─(부족)→ request_human_clarification
        → draft_schema → assess_schema_quality
              ├─ enough ──────────────────────▶ 종료 (Schema_proto.yaml)
              ├─ needs_human_review ──▶ review_schema_with_human ──▶ 종료
              └─ needs_completion ───▶ complete_and_validate ────▶ 종료 (Schema_validated.yaml)
```

| 단계 | 내용 |
|---|---|
| `fetch_paper_context` | 논문 텍스트(`paper_*.md`), 그림 힌트, 스키마 규칙(`Schema_v5.yaml`)을 MCP 도구로 수집 |
| `assess_input_readiness` | 사용자 요청이 충분히 구체적인지 판단 → 부족하면 `request_human_clarification`(HITL) |
| `draft_schema` | `build_schema_draft_langchain`: VLM(`vlm_extract_*_image_info`)으로 그림에서 정보 추출 + LLM으로 스키마 초안 YAML. `finalize_schema_from_draft`가 정리(**블록 ID 4글자 초과 시 `B<n>`으로 정규화**, `block_ids.py`) |
| `assess_schema_quality` | MCP `schema_validation` 사전검사 + `schema_quality_report`. 판정: `enough` / `needs_completion`(구조 오류·실행 필수 항목 누락) / `needs_human_review`(검토할 항목 존재) |
| `complete_and_validate` | `part1_validate_and_complete`: 최대 3회 반복 { `validate_schema_for_execution` → 누락 항목 → `retrieve_evidence`(논문에서 근거 창 검색) → `llm_complete_missing`(JSON 패치 생성) → `apply_json_patch` }. 결과는 `Schema_validated.yaml` + 보고서 JSON |
| `review_schema_with_human` | 검토 항목을 사용자에게 질문 (아래 EDC 분기 참고) |

산출물: `Schema_proto.yaml`(초안) 또는 `Schema_validated.yaml`(보완본), `part1_status.json`.

## 4. EDC가 끼어드는 지점 (모두 플래그, 기본 off)

| 지점 | 위치 | 플래그 | 동작 |
|---|---|---|---|
| 프롬프트 덧붙임 | `build_schema_draft_langchain` / `llm_complete_missing` 안에서 `edc_prompt.draft_template(...)`, `completion_template(...)` | `PART1_EDC_PROMPT=1` | 초안 프롬프트에 인용 원문·후보 값·계산식·조성 근거·물성 방법 대체 기록 요구를 덧붙임 |
| 검토 항목 선택 | `assess_schema_quality` → `_review_items_for_session` | `PART1_EDC_POLICY=1` | 끄면 기존 confidence 임계 선택기(`collect_schema_human_review_items`), 켜면 `edc_policy.policy_review_items`(근거 분류 + 영향도 + 상한 K=5). 분류 결과는 `state["edc"]`에 저장, `edc_assumption_ledger.json` 기록 |
| 질문 문구 | `review_schema_with_human` | 〃 | `edc_policy.format_question`이 항목·값·출처·인용을 표시하고 "`ID=값`으로 답하면 스키마가 바뀐다"를 안내 |
| 답변 반영 | `ep_parse` → `_apply_edc_answer` | 〃 | 엄격/느슨한 파서로 `ID=값`을 해석, 스키마 수정(원본은 `*.pre_review.yaml` 백업, `source=user`), 인식 실패 시 1회 재질문 |
| 보완 후 검토 | `edc_review_after_completion` | 〃 | `needs_completion` 경로에서 `Schema_validated.yaml`에 대해서도 검토 |
| 자유도 장부 | `dof_ledger.py` (`edc_policy`가 사용) | 항상(분석 시) | 블록별 필요 사양이 채워졌는지, 인용문이 논문 원문에 있는지 검사 |
| 가정 요약 | `chat_orchestrator._assumption_summary_block` → `edc_policy.summary_from_file` | `PART1_EDC_POLICY=1` | 파이프라인 마지막 메시지 뒤에 "[가정 요약]" 첨부 |

`edc_policy.py` 분류는 **LLM을 호출하지 않는 결정적 규칙**(인용 검사, 값 비교, 후보 목록)이다.

## 5. Part2 — 스키마 → Aspen COM 모델 (`part2_stage_functions.py`)

### 5.1 `build_session` (에이전트 루프 시작 전에 순차 실행)

```
_generate_inp_skeleton()      LLM + inp_v1.yaml(INP 문법 DB)로 초기 INP 골격 생성 (성분 ID 해석: aspen_components.yaml)
_convert_inp_to_bkp()         aspsetup.bat으로 INP → BKP 변환
_build_com_action_plan()      LLM + aspen_code_v3.yaml(COM 함수 카탈로그)로 COM 작업 계획(JSON)
_generate_com_skeleton_code() 계획 → COM 파이썬 코드 생성
_execute_com_skeleton()       코드를 실행해 Aspen 문서 `doc`을 만듦 (모듈 전역 상태)
```

### 5.2 에이전트 도구 순서

```
prepare_part2 → fetch_part2_context
→ run_repair_phase("property_method") → ("connectivity") → ("feeds") → ("block_specs")
→ final_validate → assess_final ─(검토 필요)→ review_with_human → [repair_with_human_feedback → final_validate → assess_final]
→ write_result
```

### 5.3 `repair_phase(phase)` — 단계별 수리 루프
각 단계마다:
1. **스키마 기반 결정적 수리** (`valid_*_schema_repair.py`: 물성 방법, 연결, 피드, 블록 사양을 스키마 값으로 직접 적용). block_specs는 사전 검증에서 걸린 블록에 한정.
2. **검증기 실행** (`valid_*.py` + `valid_*_rules.yaml`, 공용 위치 `2608 수정/`) — `run_validator_phase`.
3. 통과 못 하면 최대 3회: LLM이 **패치 계획**(`_generate_patchplan_for_phase`) → 안전 검사(`safety_check_patchplan`, 허용 함수 목록 `PHASE_FUNCTION_ALLOWLIST`) → **COM 보정 코드** 생성 → 실행 → .bkp 저장 → 재검증.

### 5.4 최종 단계
- `final_validate_node`: 전체 검증(`final_all`). 수리가 있었으면 저장+Aspen 실행(`_run_save_and_check`)으로 `.his` 생성, 없으면 초기 모델을 실제 실행해 `.his` 생성(Part3 입력).
- `assess_final_node` → MCP `repair_assessment` → 사람 검토 필요 여부. 검토 시 approve/revise(수리 요청)/stop.
- `write_result_node`: `part2_result.json` 기록, Aspen 문서 닫기.

phase13에서 추가·수정된 곳: 성분 ID 매핑(원래 `aspen_id` 등록), `stream_set_total_flow`의 질량 기준 단위 처리, `check_feed_flow_units`(Aspen `TOTFLOW.UnitString`을 읽어 스키마 flow basis와 대조, 한 번 정정 후 재확인, 실패 시 `feed_flow_unit_mismatch`). `valid_feed_schema_repair.py`가 import 시점에 묶어 두던 함수 참조도 교체.

산출물: `.bkp`(`com_proto_initial.bkp` 또는 `com_proto_repaired.bkp`), `.his`, `part2_result_iter1.json`.

## 6. Part3 — 실행 로그 진단·패치 (`part3_stage_functions.py`)

```
run_aspen_check → parse_his ─(severe·error 없음)→ early_exit → assess_result → write_result
      │
      └(있음)→ [ begin_repair_attempt(최대 3회, 코드로 강제)
                 → search_error_docs(RAG) → diagnose_issue → plan_patch
                 → generate_patch_code → apply_patch → rerun_and_check ] × N
              → assess_result ─(검토 필요)→ review_with_human → write_result
```

- `run_aspen_check`: .bkp를 다시 열어 정상 로드되는지 확인하고 `.his`/`.inp` 경로 확정.
- `parse_his`: `** SEVERE ERROR / ERROR / WARNING` 블록 추출·집계. Part2 결과로 이미 오류 0임이 확인되면 파싱을 생략하고 조기 종료(`skip_by_part2_result`).
- 수리 사이클: 오류 문구 분류·검색어 생성 → 문서 RAG(`Aspen_error handling*` 지식) → LLM 진단(JSON) → 패치 계획 → COM 코드 → 적용 → 재실행·재파싱. 안전 검사는 `part3_patch_safety.py`.
- `begin_repair_attempt`가 사이클 수를 세어 상한 초과 시 `allowed=false`를 돌려주므로, 프롬프트가 아니라 **코드 수준에서** 무한 루프를 막는다.

산출물: 최종 `.bkp`, `part3_result.json`. 이후 챗봇이 최종 파일 경로와 가정 요약을 출력하고, Gradio가 `.bkp`를 다운로드 파일로 제공.

## 9. 논문 관점에서 코드를 볼 때 (위치 요약)

- 실험의 "켜짐/꺼짐" 대상은 **Part1의 두 지점**(프롬프트, 검토 항목 선택)이다. Part2/3 로직은 EDC와 무관하게 동일하다.
- 정답 없이 재는 지표를 만들 때 쓸 수 있는 기존 재료:
  - 근거 추적성: `dof_ledger.py`의 인용 검사, `edc_assumption_ledger.json`
  - 실행 간 불안정성: `analyze_2e.py`(구조 서명·값 안정성), `run/2e_manifest.csv`
  - 유효값 감사(미구현): Part2 `check_feed_flow_units`가 이 아이디어의 일부 선례(피드 유량 단위만 해당)
- 새 베이스라인(B0/B1)은 이 파이프라인과 별개의 하네스로 둔다: 같은 논문·같은 Aspen 환경에서 일반 LLM+도구로 실행하고, 같은 지표 스크립트로 채점.
